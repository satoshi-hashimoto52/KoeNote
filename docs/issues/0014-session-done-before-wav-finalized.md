# Issue #0014: session.json が done になった後も WAV の最終処理が続く

- 状態: 未調査
- 起点コミット: `653a9db`（0013 修正後にも残る）
- 種別: 調査 / 整合性（**データ破損は確認されていない**）
- 重要度: 中。**非ブロッキング**。C-3 の合格を妨げない
- 発見経緯: 2026-08-28、C-3 再試験の記録を突き合わせて気付いた
- 関連: [#0013](0013-wav-header-regression-on-app-exit.md)（recorder ライフサイクル）

## 事象

C-3 再試験のセッションで、完了表示と実ファイル確定の時点がずれていた。

| 項目 | 時刻 |
| --- | --- |
| `session.json` の `ended_at` | **15:23:16** |
| `recording.wav` の最終 mtime | **15:25:26** |
| 差 | **約 2 分 10 秒** |

`status = done` になった後も、約 2 分 10 秒にわたって WAV への書き込みが続いていた。

**最終的に FD は解放され、データ破損もない。**アプリ終了前後で
`afinfo` 417.920 秒・SHA-256 `a00ac4b0…`・size 13,373,484 bytes がいずれも変化していないことを確認済み。
本 Issue は「完了表示と実ファイル確定の時点が一致していない」ことのみを扱う。

## なぜ問題になりうるか

`status = done` は利用者にとって「保存が終わった」という合図である。
その時点でファイルがまだ確定していないと、次の操作が壊れる可能性がある。

- 完了直後に `recording.wav` を **Finder で移動 / リネーム**した
- 完了直後に **共有・アップロード**した（途中までのファイルを配ってしまう）
- 完了直後に **アプリを終了**した（0013 で見たとおり、終了処理が最後の書き込みを担う）
- 完了直後に **外部ツールがファイルを読んだ**

いずれも今回は実害が出ていないが、**タイミング次第で内容が変わりうる**状態である。

## 調査すべき順序

`done` へ更新するまでの各処理の完了順序を確認する。

1. `session.json` を `done` に更新するのは誰か（Renderer の `/api/session/finalize` 呼び出し）
2. WebSocket の `stop` 受信から `session_final` 送出までの流れ
   - `stop_event.set()` → `await driver`
   - `drain_on_stop()`（Whisper の末尾処理。窓を最大 `DRAIN_MAX_WINDOWS` まで走査する）
   - `recorder_registry.release(recorder)`（0013 で `finalize()` の前へ移した）
   - `session.finalize()` → `session_final` 送出
3. Renderer が `session_final` を受けてから `/api/session/finalize` と
   `/api/session/repair_audio` を呼ぶまでの流れ
4. `repair_audio` が走る時点で recorder が確実に閉じているか
5. `AsyncWavAppender.close()` の書き込みスレッド join（最大 10 秒）が
   どの時点で完了するか

**仮説（未検証）**: 差の大半は `drain_on_stop` による末尾の再推論と、
その後の `repair_audio` によるヘッダ書き戻しではないか。
`ended_at` が先に書かれ、実ファイルの最終書き込みが後になっている可能性がある。
ただし 2 分 10 秒は長く、他の要因が絡んでいる疑いもあるため、**推測で断定しない。**

## 期待する挙動（案）

次のいずれかで、表示と実体を一致させる。

1. **すべての書き込みが完了してから `done` にする**（もっとも素直。停止から done までの体感時間は延びる）
2. `done` とは別に「音声ファイル確定済み」を示す状態を持ち、UI に出す
3. 完了までの間、UI 側でファイル操作を促さない（「保存中」の表示を出す）

## 必要なテスト

- 停止完了時点で `recording.wav` の mtime が以後変化しない
- `status = done` の時点で WAV の FD が残っていない（0013 で追加済み）
- `done` 後にファイルを移動しても、以後の書き込みで復活・破損しない
- 停止から `done` までの所要時間が記録・観測できる

## 受け入れ試験への影響

**なし。** C-3 / E-2 の合格条件はいずれも満たしており、判定は変更しない。
本件は完了表示と実体の同期に関する改善であり、データ破損は確認されていない。
