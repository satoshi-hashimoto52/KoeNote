## プロセス操作の安全手順

`kill` を使う試験では、必ず次の 2 段階で行う。`$(pgrep ...)` の結果へ直接 `kill` しない。

1. 対象 PID を一覧表示して確認する。

   ```bash
   pgrep -fl "uvicorn main:app"
   ```

2. 表示が 1 件であることと、コマンドラインが `-m uvicorn main:app --host 127.0.0.1 --port 8000` であることを目視で確認する。
3. 確認した PID を手で入力して実行する。`<PID>` は 1 で表示された数値に置き換える。

   ```bash
   kill -9 <PID>       # 強制終了（C-3, E-2）
   kill -STOP <PID>    # 一時停止（C-2）
   kill -CONT <PID>    # 再開（C-2）
   ```

複数件表示された場合は、どれが試験対象かを特定できるまで `kill` を実行しない。
外部で手動起動した Backend と Electron が spawn した Backend が同時に動いていることがある。

## A. 長時間録音

### A-1. 実マイクによる 60 分以上の録音

手順

1. タイトル・保存先を入力し「文字起こし開始」を押す。
2. 実マイクに向かって断続的に発話しながら 60 分以上放置する（会議音声の再生でも可）。
3. 15 分ごとに診断ログの「録音」「処理済み」「遅延」「破棄」「窓」を記録する。
4. 15 分ごとに Activity Monitor で Python プロセスの RSS を記録する。

期待結果

- 状態が `録音中` のまま 60 分以上継続する（20〜30 分での停止が起きない）
- 診断ログの「遅延」が時間経過で増え続けない（数秒以内で上下する）
- 「破棄」が 0.0s のまま
- Python の RSS が横ばい（モデル常駐分の約 300〜400MB で安定し、単調増加しない）
- `transcript.txt` が追記され続ける
- 「最終音声受信」「最終文字起こし」の時刻が更新され続ける

記録

| 経過 | wav 長と実経過の差 | Python RSS | Electron 合計 RSS |
| --- | --- | --- | --- |
| 0 分（1:21） | +2.21 s | 998.8 MB | 502.3 MB |
| 15 分（15:05） | +1.42 s | 668.8 MB | 510.7 MB |
| 30 分（30:17） | +2.99 s | 548.9 MB | 453.6 MB |
| 45 分（45:08） | +4.38 s | 701.5 MB | 458.1 MB |
| 60 分（60:21） | +1.13 s | 519.1 MB | 453.4 MB |
| 停止後（16:37:28） | 最終 +2.30 s | 399.1 MB | 510.3 MB |

診断ログの「遅延」は UI 内のリングバッファにのみ存在し、外部から取得できなかったため未記録。
代替指標として wav 長と実経過時間の差を記載した。数秒内で上下し、時間経過による累積はない。
Backend ログの `lag` は初回モデルロード時の 4.5 秒（window=7）を除き 1.3〜3.9 秒で推移し、増加傾向なし。

Python RSS の 0 分値 998.8 MB はモデルロード直後の一時的な確保で、以降 519.1 MB まで減少した。
単調増加は見られない（60 分値が全測定点の最小）。ただしチェックリストの期待レンジ
（約 300〜400 MB）よりは高いため、レンジの妥当性は別途検討の余地がある。

## B. 入力側の異常

### B-1. 一時的な無音（誤検知しないこと）

手順

1. 録音中に 90 秒間まったく発話しない（マイクは有効なまま）。
2. 発話を再開する。

期待結果

- 異常ポップアップが出ない（状態は `録音中` のまま）
- 警告音が鳴らず、OS 通知も出ない
- 診断ログの「処理済み」が無音中も進み続ける
- 発話再開後、続きが `transcript.txt` に追記される
- 無音区間の文字起こしが空（ハルシネーションが出ていない）

確認理由: 文字起こし停止の判定（60 秒）は `processed_audio_seconds` を見ており、無音でも進むため誤検知しない。

#### 判定の仕組み

ウォッチドッグは 3 層あり、90 秒の無音で誤発火しうるのは 3 つ目だけ。

| 層 | 閾値 | 定数 | 無音時の挙動 |
| --- | --- | --- | --- |
| キャプチャ停止 | 3 秒 | `CAPTURE_TIMEOUT_MS` | マイクは動き続けるので発火しない |
| Backend 無応答 | 8 秒 | `HEARTBEAT_TIMEOUT_MS` | heartbeat が流れ続けるので発火しない |
| 文字起こし停止 | **下表のとおり** | `TRANSCRIPTION_STALL_MS` | **ここが判定対象** |

**文字起こし停止の閾値（[`0011`](issues/0011-transcription-stalled-false-positive.md) の修正後の正確な仕様）**

| 状態 | 閾値 | 理由 |
| --- | --- | --- |
| **初回進捗前**（`processed_audio_seconds` がまだ 0） | **180 秒** | Whisper モデルのロードと初回推論を考慮する。Backend 再起動直後はモデルが未ロードで特に長い |
| **初回進捗の確認後** | **60 秒** | 通常の文字起こし停止判定 |
| **`session_id` の変更 / `processed` の巻き戻り** | 監視基準をリセットし、**初回進捗前の 180 秒猶予を再適用** | 別セッションの値と比較すると誤検知するため |

境界の比較は **`>=`**（閾値ちょうどで発火する）。
キャプチャ停止 3 秒と Backend 無応答 8 秒は**変更なし**。

1. `no_speech_prob` 判定を変更したため、認識結果が以前より増える（従来捨てていた確信度の高い音声を保持するようになった）。以前のログと比較する場合はこの差を考慮する。
2. リアルタイム経路は ffmpeg を使わない。ffmpeg 未検出のバナーが出ても、リアルタイム文字起こしには影響しない（音声ファイルからの文字起こしのみ影響する）。
3. 診断ログを閉じると `metrics` の送信が止まる。数値を追う試験中は開いたままにする。
4. `medium` モデルは推論時間を実測していない。使用する場合は、診断ログの「遅延」が増え続けないことを A-1 で必ず確認する。
5. **試験開始前に入力デバイス名を必ず確認する。** このマシンには BlackHole 2ch（仮想ループバック）と
   Microsoft Teams Audio が入っており、これらを選ぶとマイクの肉声ではなくシステム音声が録音される。
   画面右下の `入力: …` と診断ログ 1 行目の `入力デバイス=` は `getUserMedia` が実際に許可した
   `track.label` なので、この値で確認する。詳細は `docs/issues/0005-input-device-misselection.md`。
